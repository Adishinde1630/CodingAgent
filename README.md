# AI Coding Agent

A small, end-to-end **AI coding agent**: describe a coding task in plain English and it inspects a codebase, reads the relevant files, writes a plan, edits the code, shows a Git-style diff, runs `pytest`, and reports what actually happened.

## 1. Project overview

Built with **Streamlit** (UI), **LangGraph** (agent workflow/state), the **Groq API** (LLM) and plain Python tools for everything that touches files. The LLM *decides*; deterministic tools *act*. The final report is built from real tool output, so the agent never claims a change or a test result that did not happen.

## 2. Assignment objective

Accept a natural-language coding request → inspect a sample codebase → read multiple files → identify relevant files → generate a plan → modify code → explain the change → show a diff → run meaningful validation → display the final result.

## 3. Features

- Plan generated by the LLM from the *real* code (shown before any file is touched)
- File inspection tools: list, read, read-many, search, tree/outline
- Relevant-file selection (keyword ranking + LLM choice, validated against the real file list)
- Safe writes inside a sandboxed workspace copy, original content saved, one-click rollback
- Real Git-style unified diff (`diff --git a/... b/...`) computed from saved originals
- Real `pytest` run (captured stdout/stderr/exit code, timeout) + syntax and import checks
- Automatic repair loop: failing test output is fed back to the model (configurable, default 1 retry)
- Optional auto-rollback if validation fails; manual "Revert all changes" button
- Clear errors: missing/invalid key, rate limits, unavailable model, empty task, bad paths, invalid LLM code, timeouts

## 4. Architecture

```
Streamlit UI (app/main.py)
      │  streams node-by-node progress
      ▼
LangGraph agent (app/agent.py, state in app/state.py)
      │ prompts (app/prompts.py)          │ tools (app/tools.py)
      ▼                                   ▼
Groq client (app/llm.py)        FileManager (sandbox)  ·  code_analyzer  ·  diff_manager  ·  validator
                                          │
                                          ▼
                       temp copy of sample_project/ (one per browser session)
```

## 5. Agent workflow

```
understand_task → inspect_codebase → select_relevant_files → create_plan → generate_changes
→ apply_changes → generate_diff → run_validation ─┬─ passed / out of attempts → summarize_result
                                                  └─ failed → generate_changes (repair loop)
```

| Node | What happens | Tools used |
|---|---|---|
| `understand_task` | LLM turns the request into a summary, task type and search keywords | – |
| `inspect_codebase` | Lists files, builds the tree and signature outlines (not full source) | `list_files`, `read_files` |
| `select_relevant_files` | Keyword search + LLM pick (max 8, validated), then reads the chosen files | `search_code`, `read_files` |
| `create_plan` | LLM writes a plan from the real file contents | – |
| `generate_changes` | LLM returns full new content per file (+ explanation) | `read_files` (current state) |
| `apply_changes` | Syntax-checks Python first, validates paths, saves originals, writes | `write_file` |
| `generate_diff` | Unified diff of original vs. current | `get_diff` |
| `run_validation` | Syntax + import checks, then pytest | `validate_project`, `run_tests` |
| `summarize_result` | Optional rollback; LLM writes wording from verified facts; UI shows tool data | `rollback` |

Any fatal error (e.g. invalid API key) routes straight to the end and is shown in the UI.

## 6. Technology stack

Python 3.11+ · Streamlit · LangGraph · `groq` SDK · pytest · python-dotenv · `difflib` for diffs.

## 8. Groq API setup

1. Create a key in the [Groq Console](https://console.groq.com/keys) (keys start with `gsk_`).
2. Put it in `.env` (local) or Streamlit Secrets (deployment). **Never commit it.**
3. Model is configurable with `GROQ_MODEL`. Default: `openai/gpt-oss-20b`.

> If you see a "model is not available" error, a model may have been retired - set `GROQ_MODEL` to a current model from Groq's model list. A rate-limit response stops the current run without retrying or starting code generation; wait for the indicated Groq limit to reset and try again. A "request too large" response may require a smaller task.

## 9. Environment variables

| Variable | Required | Description |
|---|---|---|
| `GROQ_API_KEY` | yes | Groq API key (read from env, `.env`, or Streamlit Secrets) |
| `GROQ_MODEL` | no | Model name, default `llama-3.3-70b-versatile` |

For `GROQ_API_KEY`, a non-placeholder value in the project `.env` takes precedence
over an inherited environment variable; otherwise the app falls back to the
environment variable and then Streamlit Secrets.

## Working with your own project

1. Start the application with `streamlit run app/main.py`.
2. Select **Upload ZIP** under **Project Source**.
3. Upload a ZIP containing your project files.
4. Enter a coding task for that project.
5. Click **Run Coding Agent**.
6. Review the generated plan in **Agent Plan**.
7. Review changed files in **Changes**.
8. Review the generated patch in **Diff**.
9. Review syntax and test results in **Validation**.
10. Read the outcome in **Final Summary**.

The original uploaded ZIP is never modified. The agent works only in a private temporary workspace, which can be reset from the sidebar. ZIP uploads are limited to 500 MB; extraction still rejects unsafe paths and links, filters blocked or unsupported files, and enforces entry-count, nesting, and extracted-size limits.

## 14. Example agent workflow

1. **Inspect**: tree + outlines of `app.py`, `models.py`, `validators.py`, `tests/`.
2. **Select**: `app.py` (registration), `validators.py` (validation), `tests/test_app.py`, `tests/test_validators.py`.
3. **Plan** (shown in the UI before any edit): add `is_valid_email`, call it from `register_user`, add unit + API tests, run pytest, review diff.
4. **Apply**: files written inside the workspace copy; originals saved.
5. **Diff**: real `diff --git` output for each changed file.
6. **Validate**: `pytest` really runs; exit code and output are displayed (✓ Tests executed / ✓ Tests passed or ✗ Tests failed).
7. **Summary**: summary, files modified (from the filesystem), why, validation, diff, limitations.

## 15. Deployment (Streamlit Community Cloud)

1. Push this repo to GitHub (`.env` is git-ignored - verify with `git status`).
2. On [share.streamlit.io](https://share.streamlit.io) create an app: repository = yours, **Main file path = `app/main.py`**, Python **3.11+** (Advanced settings).
3. In **App settings → Secrets** add:
   ```toml
   GROQ_API_KEY = "your_real_key_here"
   GROQ_MODEL = "llama-3.3-70b-versatile"
   ```
4. Deploy. Secrets are exposed to the app through `st.secrets` / environment variables - nothing is committed to GitHub. No absolute paths are used; each session works on its own temp copy of `sample_project/`.

Other platforms (Render, Railway, Docker): `pip install -r requirements.txt`, set `GROQ_API_KEY` as an environment variable, start with `streamlit run app/main.py --server.port $PORT --server.address 0.0.0.0`.

## 16. Assumptions

- The sample project is the target codebase; each browser session edits a private temp copy, so the repository's sample files are never modified.
- Tasks are small enough that the relevant files (≤ 8, ≤ 100 KB each) fit in the model's context.
- Python files are returned in full by the model rather than as patches.

## 17. Limitations

- Passing tests only proves what the tests check; review the diff.
- The agent can add/modify files but has no delete or shell tool; the model could still weaken or rewrite tests (visible in the diff).
- Only text files with allowed extensions are supported; large projects would need smarter retrieval than keyword search.
- Test code runs in a subprocess with a scrubbed environment and a timeout, but this is **not** a hardened sandbox (use containers for untrusted multi-tenant deployments).
- Quality depends on the Groq-hosted model; the build environment for this repo had no access to Groq's API, so the live call path is verified only through mocked-SDK tests, the real SDK's error handling, and the scripted-LLM tests.

## 18. Security considerations

- The API key is read from the environment/secrets only; never hard-coded, never rendered, redacted from errors; the test subprocess does not receive it.
- All paths go through `FileManager.resolve`: no absolute paths, `..`, null bytes, symlink escapes, `.env*`, `.git`, `.venv`, `__pycache__`, key/cert files, binary or unsupported types; files that look like they contain keys are refused for read *and* write.
- Size limits (100 KB/file, 500 files, 80 K chars of context); subprocesses have timeouts.
- The LLM never runs shell commands; it can only return file contents, which are syntax-checked before writing.
- Repository text is wrapped in tags and treated as untrusted data in prompts (prompt-injection mitigation).
